2026 · Python · Singer SDK · OpenAI Codex

tap-usgs-earthquakes: a Singer connector for the USGS Earthquake Catalog

What it does
It pulls live earthquake events from the public USGS API into any Singer or Meltano destination. It needs no API key and no config: meltano run tap-usgs-earthquakes target-jsonl streams real data in about a minute.
How I used Codex
  • An AGENTS.md with hard rules: run with an empty config, never request more than 20,000 rows, keep unit tests offline, and run the full check before calling a task done
  • A phased build: Codex researched the live API and recorded evidence and fixtures before it wrote any tap code
  • A review round: an independent review found that Meltano was silently turning off incremental sync, and Codex fixed that and the other findings
  • Codex also set up CI and trusted PyPI publishing through GitHub OIDC, and wrote the Meltano Hub listing
Hard parts
  • Incremental sync on updated when the API can only sort by event time or magnitude. The stream is marked unsorted, and state moves forward only after a full run
  • Old events get revised later, so incremental runs send updatedafter together with an explicit starttime
  • The /count endpoint sizes each time window, which is split in half until it fits under the 20,000-row limit. Windows with no changes are skipped
Tested
Ruff, mypy, offline fixture tests, the Singer SDK’s 26 standard tap tests against the live API, and CI on Python 3.10 and 3.12.

Meltano · 2026–now · Applied AI

Self-healing data pipelines: an agent finds the failure, writes the fix, and a person approves it

Problem
When a pipeline failed, an engineer had to notice it, read long logs, find the cause and write the fix. The customer’s data stayed stale the whole time.
What I built
  • A monitoring agent that watches every pipeline and acts on a failure before a customer reports it
  • For each failure, the agent finds the cause, writes the fix and opens a pull request. An engineer reviews it and merges, so a person stays in the loop
  • AI diagnosis for each failed run, with the cause and next steps shown in the app and in the alert email
  • Context preparation that runs in parallel, is cached, and stays inside the model’s 200K-token limit
  • MCP tools that let customers’ own AI agents search the Meltano knowledge base and work with their pipelines
  • An agent-assisted engineering practice: custom skills, commands and hooks for coding agents, plus MCP integrations with Linear and GitHub, for bug triage, code review and incident investigation
Result
Time to fix a failed pipeline fell from days to under an hour. A failure turns into a reviewed fix instead of a ticket waiting in a queue.
Stack
Python, Claude, MCP, GitHub API, Linear

What I built

Blinkit · 2021–2024 · Quick commerce

Event-driven systems behind 10-minute delivery, from the warehouse dock to the customer’s door

  1. Warehouse
    1. Receive. The truck is unloaded and every crate is scanned.
    2. Validate. Each item is checked against the purchase order it was raised for.
    3. Put away. Stock goes to its aisle, rack and shelf.
    4. Plan. Put lists come from each dark store’s demand, oldest expiry first.
    5. Pick and bill. Items are crated one by one and billed as a B2B sale.
    6. Load. Crates are sorted to trucks by the volume of each item and crate.
  2. Transit
    1. Dispatch. The truck checks out and GPS tracks it to the dark store.
    2. Arrive. The store sees which truck and driver came, and checks the seal.
  3. Dark store
    1. Receive. Crates are unloaded, scanned, sorted and shelved.
    2. Pick. Each customer order becomes a pick list.
    3. Hand off. The picker puts the order on a rack and scans its QR code.
    4. Deliver. The rider scans the order out and marks it delivered at the door.
Problem
A 10-minute promise only holds if every item is in the right dark store before anyone orders it. That means stock, crates, trucks and riders tracked at every handoff, with nothing lost between them.
What I built
  • Led a pod of 4 engineers on middle-mile tracking: truck dispatch, live GPS, seal checks and store arrival
  • Asynchronous Kafka pipelines for real-time inventory, crate, asset and order events
  • A new dark-store system in Java and Spring Boot for unloading, shelving, auditing and picking
  • Load planning by item and crate volume, and demand-based put lists that ship the oldest stock first
  • Invoice registration in FastAPI for B2B billing and compliance
Result
Live visibility of stock in transit across 20 warehouses, about 600 dark stores and about 4,000 truck trips a day.
Stack
Java, Spring Boot, Kafka, FastAPI, PostgreSQL, Redis
